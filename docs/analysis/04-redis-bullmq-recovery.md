## Рекомендований дизайн

### 1. Принцип
Усе, що має бути виконане в майбутньому, записується в Postgres **в тій самій транзакції, що й бізнес-зміна**. Redis лише прискорювач; після відновлення задачу знаходить періодичний **sweeper** (опитування БД). Проблеми dual-write немає: якщо `queue.add` після commit не вдався, нічого не втрачено.

Усі порівняння часу через `clock.now()` як параметр SQL; `now()` у SQL не використовується (інакше FakeClock не працюватиме, а годинники БД і worker розійдуться).

### 2. Що в Postgres

| Таблиця | Призначення | Ключові обмеження |
| --- | --- | --- |
| `reminders` | `appointment_id`, `kind` (`h24`/`h2`), `start_snapshot` timestamptz, `due_at`, `cancelled_at`, `enqueued_at` (рішення прийняте, лист у outbox створено), `skipped_at` | `UNIQUE (appointment_id, kind, start_snapshot)`; часткові індекси на `due_at` для `enqueued_at IS NULL AND cancelled_at IS NULL AND skipped_at IS NULL` |
| `email_outbox` | `dedupe_key`, `to`, `template`, `payload`, `message_id`, `status` (`pending`/`sent`/`dead`), `attempts`, `next_attempt_at`, `claimed_by`, `claimed_until`, `sent_at` | `UNIQUE (dedupe_key)`; детермінований `message_id` (`<outbox-id@clinic.local>`) |
| `sick_days` | `doctor_id`, `clinic_id`, `date`, `created_by` | `UNIQUE (doctor_id, clinic_id, date)` (узгодити з `schedule_exceptions` блоку 1: достатньо одного з двох) |
| Існуючі | `appointments.hold_expires_at` (статус `held`); `waitlist_offers.expires_at`, `status` | обмеження блоків 1 і 5 |

- Окремі job-таблиці для зняття броні й закінчення пропозиції не потрібні: sweeper читає `hold_expires_at` та `expires_at` напряму (YAGNI).
- `UNIQUE (appointment_id, kind, start_snapshot)` робить рішення «надіслати» exactly-once.
- Дедуплікація листів лікарняного: `dedupe_key = sick:{appointment_id}`.
- In-app нагадування (`:34`) це рядок у `notifications`, створюється в тій самій транзакції, що й outbox-запис.

### 3. Що в Redis (лише тригери)
Черги BullMQ:
- `timers`: `hold-expiry`, `reminder-24h`, `reminder-2h`, `waitlist-offer-expiry`;
- `mail`: `email-send`.
- Окремої черги для лікарняного немає: він обробляється синхронно в api (п. 7), `mail` лише тригерить доставку.

Правила:
- **Payload** лише `{ subjectId, kind }`; обробник перечитує стан із БД.
- **`jobId` детермінований**, напр. `reminder-24h_{apptId}_{startEpoch}`. Роздільник `-` або `_`, не `:` (BullMQ забороняє `:` у кастомному id). Повторний `add` з тим самим id ігнорується.
- **Delay** = `max(0, due_at - clock.now())`.
- **Enqueue після commit**, у `try/catch` з коротким таймаутом (~200 мс). Помилка Redis логується, бронювання не падає.
- У api для Queue `enableOfflineQueue: false`: при недоступному Redis виклик падає одразу, а не висить.

### 4. Життєвий цикл подій

**Створення запису** (`booked`). В одній транзакції вставляються `reminders` h24 і h2 з `due_at = start_snapshot − 24h/2h` (абсолютні інстанти). Якщо `due_at <= now`, рядок одразу `skipped_at` (Q1). Після commit best-effort `queue.add`.

**Перенос** (інв. 8, приймання 9). В одній транзакції старі `reminders` отримують `cancelled_at`, вставляються нові з новим `start_snapshot`. Старе нагадування не піде з двох причин: (1) рядок скасований; (2) при обробці перевіряється `appointments.starts_at = reminders.start_snapshot AND status = 'booked'`. Задача зі старим `jobId` у Redis може відпрацювати, але нічого не зробить.

**Відміна.** Транзакція ставить `cancelled_at` на всі нагадування запису; скасований запис не проходить перевірку статусу.

**Обробка due-нагадування** (одна транзакція, без SMTP усередині):
1. `SELECT … FROM reminders WHERE id=$1 AND enqueued_at IS NULL AND cancelled_at IS NULL FOR UPDATE SKIP LOCKED`.
2. Перевірити актуальність запису (час і статус).
3. Вставити `email_outbox` з `dedupe_key = reminder:{id}`, in-app notification, виставити `enqueued_at`.
4. Commit.

Конкурентні перенос чи відміна оновлюють той самий рядок `reminders` і чекають транзакцію sweeper: лист або пішов до відміни, або не пішов зовсім.

**Доставка листа** (`email-send`, at-least-once):
1. Claim: `UPDATE email_outbox SET claimed_by, claimed_until = $now+lease WHERE id IN (SELECT … WHERE status='pending' AND next_attempt_at <= $now AND (claimed_until IS NULL OR claimed_until < $now) FOR UPDATE SKIP LOCKED LIMIT n) RETURNING *`.
2. SMTP-відправка поза транзакцією, з детермінованим `Message-ID`.
3. `UPDATE … status='sent', sent_at`.
4. Помилка: `attempts++`, `next_attempt_at` за експоненційним backoff; після N спроб `dead` (Q14).

**Чесні межі гарантій:**
- Рішення «створити лист» exactly-once (UNIQUE).
- Фізична доставка at-least-once: якщо worker впав після SMTP 250 OK, але до `sent_at`, після спливу lease лист піде вдруге. Це вікно (мілісекунди) без підтримки отримувача усунути неможливо; тому детермінований `Message-ID`, а заглушка може дедуплікувати за ним (Q3).
- Lease довший за максимальний час SMTP-виклику (таймаут 10 с, lease 60 с), щоб здорову копію не «перехоплювала» інша.

### 5. Sweeper і відновлення після втрати Redis

**Основний механізм:** цикл у worker з інтервалом 5 с (конфіг). Кожен прохід:
- hold-expiry: `appointments WHERE status='held' AND hold_kind='checkout' AND hold_expires_at <= $now`, `FOR UPDATE SKIP LOCKED`, пакетами (~100): перехід у `cancelled` з історією й подією для сітки. **Рядки `hold_kind='waitlist_offer'` не чіпає** (їх обробляє sweeper блоку 5 з каскадом; див. блок 5 Q12);
- due-нагадування (п. 4);
- `waitlist_offers` з `expires_at <= $now` і статусом `pending`: `expired` і виклик `releaseSlot` блоку 5 в тій самій транзакції;
- `email_outbox` due для доставки.

Індекси часткові за `due_at`, тож прохід дешевий і на сіді.

**BullMQ це прискорення.** Delayed job викликає той самий `processDue(kind, id)`, що й sweeper: спільна логіка й ідемпотентність. Без Redis затримка ≤ інтервалу sweeper (≤5 с).

**Коректність без sweeper:**
- Сітка вважає вільним прострочений checkout-холд (`hold_kind='checkout' AND hold_expires_at <= clock.now()`), а підтвердження перевіряє `hold_expires_at > clock.now()`; спізніле підтвердження відхиляється (інв. 4). Прострочений offer-held лишається зайнятим, доки його не обробить sweeper блоку 5 (`00-decisions.md`, R2).
- Бронювання на слот у транзакції «ліниво» знімає прострочену бронь (reap-on-write). Exclusion у БД не залежить від `now()`.
- Sweeper лише чистить дані й шле події.

**Старт worker** (приймання 10, `:160`):
1. Спочатку повний reconcile до запуску BullMQ Worker: цикл по всіх прострочених `due_at <= now` до вичерпання.
2. Ре-seeding: для всіх `pending` з `due_at` у межах горизонту (~2 год) `queue.add` з детермінованим `jobId` і `delay`.
3. Запуск BullMQ Worker і періодичного sweeper.

**Детекція втрати Redis:**
- Worker при старті `SET clinic:epoch <uuid> NX`; кожні ~10 с `GET clinic:epoch`. Якщо ключа немає (FLUSHALL), повторний ре-seeding і новий epoch. Те саме при події `ready` після перепідключення ioredis.
- Це оптимізація затримки; sweeper працює незалежно.

**Налаштування:**
- Redis у compose: `maxmemory-policy noeviction` (потрібно BullMQ), `appendonly yes`, `appendfsync everysec`. AOF зменшує втрати, але правильність на ньому не будується.
- `defaultJobOptions`: `removeOnComplete: { age: 3600, count: 1000 }`, `removeOnFail: { age: 7*86400 }`, `attempts: 5`, `backoff: { type: 'exponential', delay: 1000 }` (для пошти 10 000).
- Worker: `lockDuration` 30 с, `stalledInterval` 30 с, `maxStalledCount` 1, `maxRetriesPerRequest: null` (вимога для Worker-зʼєднання).
- Graceful shutdown: SIGTERM → `worker.close()` → закриття БД.
- `jobId` містить `start_snapshot`; завершені job зі збереженим id не блокують нові інтенти, бо id унікальні.

### 6. Кілька копій worker (інв. 10, приймання 11)
Три рівні захисту, кожен ідемпотентний:
1. **BullMQ lock:** одну delayed-задачу бере одна копія; stalled-задачу може взяти інша, тож обробник ідемпотентний.
2. **`FOR UPDATE SKIP LOCKED`** у sweeper: копії не чекають одна одну й не беруть однакові рядки.
3. **Claim з lease** (`claimed_by`, `claimed_until`) для SMTP-фази поза транзакцією.

Одна задача може бути запущена двічі (stalled + sweeper), але ефект один: це гарантує UNIQUE у БД.

### 7. Лікарняний (інв. 12, приймання 13)
**Синхронна транзакція в api** (`markSickDay(doctor, clinic, date)`), бо «жодної в `booked`» має виконуватися атомарно:
1. Серіалізація: блок 1 пропонує рядкове блокування лікаря (`FOR UPDATE` проти `FOR SHARE` у бронювань); `pg_advisory_xact_lock(hash(doctor, clinic, date))` є альтернативою. Обрати одне в реалізації (блок 1 перевагу віддає рядковому блокуванню).
2. `INSERT INTO sick_days … ON CONFLICT DO NOTHING` разом із винятком розкладу (блок 1).
3. Вибрати записи дня зі статусами `held` і `booked`. Для кожного: `cancelled` з причиною `sick_day` та історією; `reminders.cancelled_at`; `email_outbox` з `dedupe_key = sick:{appointment_id}` (`ON CONFLICT DO NOTHING`).
4. Звільнені слоти й пріоритетні заявки: блок 5 (`markSickLeave` створює заявки `priority=1`, `releaseSlot` для скасування через лікарняний не викликається, бо день закритий).
5. Commit, потім best-effort enqueue `email-send`.

Повторний виклик знаходить 0 записів `booked`, нових листів немає. Скасування через лікарняний не рахується пацієнтові як пізня відміна (`:72`, Q8).

### 8. Час і Clock
- `Clock` інʼєктується в api і worker. У prod `SystemClock`; у тестах `FakeClock` (`now()`, `advance(ms)`, `set(date)`).
- Unit/integration тести запускають worker в одному процесі з тестом: `clock.advance(24h)` → `await sweeper.runOnce()` → перевірка БД. Реального очікування немає.
- BullMQ delayed рахує за годинником Redis, а не `Clock`: логіка обробника перевіряється прямим викликом `processDue`; окремий тест із справжнім Redis ставить `delay` 200 мс і перевіряє, що задача відпрацювала один раз.
- E2E між процесами (`:133-135`, `:156`): `CLOCK_MODE=db` лише поза production; годинник з таблиці `test_clock` з кешем ~100 мс (Q11).
- DST (інв. 11): `due_at` це абсолютний інстант (`start − 24h`); текст листа форматується в зоні клініки. Тест: `due_at − start = 24h` рівно й локальний час візиту в листі правильний.

### 9. Події для підписок (стик з блоком 6)
- Події «слот змінився» best-effort через Postgres `LISTEN/NOTIFY` (`NOTIFY` у транзакції, доставка після commit): не залежить від Redis і працює між api та worker.
- Payload лише id (ліміт 8000 байт); авторизація при формуванні відповіді підписки (блок 6).
- Втрата подій не критична: клієнт робить refetch сітки при реконекті й періодично.
- LISTEN потребує окремого постійного зʼєднання (не з пулу) з автоматичним reconnect.
- Redis pub/sub гірший: його втрата зламала б оновлення сітки, тоді як «Redis нічого не ламає» (`:102`).

**Загальні:** перезапуск Postgres під час sweeper; падіння SMTP (retry з backoff, після N спроб `dead`); перевірка конфігурації (`maxmemory-policy noeviction`, `removeOnComplete`).

## Ризики

1. **Дубль листа у вікні SMTP→`sent_at`.** Повністю усунути неможливо; чесно описати в README як at-least-once з детермінованим `Message-ID`. Приймання 11 проходить, бо вікно досягається лише при `kill -9`.
2. **Сід і шторм листів.** Нагадування для ~25 тис. майбутніх записів і минулих не повинні розсилатися при старті. Сід створює `reminders` лише для майбутніх `due_at`, решту позначає `skipped_at`.
3. **Годинник.** `now()` у SQL розведе FakeClock і prod. Потрібен лінт/grep у CI; FakeClock/`CLOCK_MODE=db` не може потрапити в production (guard за `NODE_ENV`).
4. **Повільний SMTP** тримає lease: короткий lease дає перехоплення й дубль, довгий дає затримку. Рекомендовано: таймаут SMTP 10 с, lease 60 с.
5. **Розрив між delayed job і sweeper** подвоює обробку, якщо обробник неідемпотентний. Усі обробники починаються з перевірки стану в БД.
6. **BullMQ `jobId`** не може містити `:`; завершений job зі збереженим id блокує повторний `add`, тож id включає `start_snapshot`.
7. **Зависання api при недоступному Redis** без `enableOfflineQueue: false` і таймауту. Тест T9.3.
8. **Зростання таблиць** `reminders` і `email_outbox`: політика очищення (Q13).
9. **Довга транзакція лікарняного** (десятки записів з історією) тримає блокування; пакетування суперечить атомарності (Q9).
10. **LISTEN/NOTIFY:** розрив зʼєднання тихо губить події; потрібні reconnect і refetch на клієнті.
11. **Скидання Redis між `commit` і `queue.add`** безпечне завдяки sweeper, але затримка до 5 с видима в e2e; тести чекають на результат, а не на точний момент.
12. **Взаємодія з блоком 5.** Generic hold-expiry не повинен чіпати offer-held (див. п. 5 і блок 5 Q12), інакше слот скасується без каскаду.

## Відкриті питання

- **Q1. Нагадування для запису, створеного менш ніж за 24 год (або за 2 год) до візиту.** Пропозиція: мінімум для запису 2 год (`:69`), тож h24 для запису <24 год пропускається (`skipped_at`), а h2 лишається; якщо `due_at` h2 уже настав у момент створення, надсилається одразу. У README.
- **Q2. Що означає «відправлено»: рішення (outbox) чи факт SMTP?** Пропозиція: два рівні: `reminders.enqueued_at` (exactly-once, UNIQUE) і `email_outbox.sent_at` (at-least-once). Тести інв. 8 рахують листи в заглушці за `Message-ID`.
- **Q3. Поштова заглушка: Mailpit чи власна?** Пропозиція: власна мінімальна SMTP-заглушка (Node `smtp-server`) з веб-сторінкою: зберігає листи, відкидає повторні `Message-ID`, віддає JSON для тестів. У README зазначити, що дедуплікація заглушки не обхід, а модель відповіді реальної пошти. Перед вибором звірити можливості Mailpit за документацією.
- **Q4. Параметри sweeper і lease.** Пропозиція: інтервал 5 с, batch 100, lease 60 с, SMTP-таймаут 10 с; константи в `packages/shared`, перевизначення env у тестах.
- **Q5. 24 год і DST: абсолютні години чи настінний час?** Пропозиція: абсолютні (`due_at = start − 24h` як інстант); текст листа показує час візиту в зоні клініки. У README «Прийняті рішення» (узгоджено з блоком 2 §7).
- **Q6. Для яких статусів надсилаються нагадування?** Пропозиція: лише `booked` (не `held`, `checked_in`, `cancelled` тощо).
- **Q7. In-app нагадування.** Пропозиція: рядок у `notifications` в тій самій транзакції, що й outbox; push через підписку best-effort, кабінет читає з БД.
- **Q8. Лікарняний: які статуси й штрафи?** Пропозиція: скасовуються `held` і `booked`; `checked_in`, `completed`, `no_show` не чіпаються; причина `sick_day` не рахується як пізня відміна й не впливає на правило 2 за 90 днів (`:72`).
- **Q9. Лікарняний: синхронно чи через чергу?** Пропозиція: скасування в одній транзакції (атомарно), листи асинхронно через outbox. Якщо записів на день більше за поріг (~500), попередження в README (реальна клініка має десятки).
- **Q10. Шина подій: Postgres NOTIFY чи Redis pub/sub?** Пропозиція: Postgres LISTEN/NOTIFY, щоб втрата Redis не ламала оновлення (узгоджено з блоком 6 Q12).
- **Q11. Як підміняти час між процесами в e2e?** Пропозиція: `CLOCK_MODE=db` (таблиця `test_clock`) лише при `NODE_ENV != production`, кеш ~100 мс; тести двигають час SQL-командою або test-only ендпоінтом, закритим у prod.
- **Q12. Як виявляти втрату Redis?** Пропозиція: epoch-ключ `clinic:epoch` (`SET NX` при старті, перевірка кожні 10 с) плюс подія `ready` ioredis; лише для ре-seeding, коректність забезпечує sweeper.
- **Q13. Retention для `email_outbox` і `reminders`.** Пропозиція: sweeper раз на добу видаляє `sent`/`done` старші за 30 днів; `dead` лишаються.
- **Q14. Що з листами, що вичерпали спроби (`dead`)?** Пропозиція: статус `dead`, лог ERROR з контекстом, видимість для реєстратора (мінімум: лічильник у адмін-списку), ручний повтор мутацією, автоповтору немає. Лічильник у `/ready` не додавати, щоб `/ready` не залежав від пошти.
- **Q15. Окремі черги для кожного типу задач?** Пропозиція: дві черги (`timers`, `mail`), типи як `name`; більше розділення спекулятивне (YAGNI).
