Спершу читай docs/analysis/00-decisions.md; він має пріоритет над блоками 01–06.

## Жорсткі обмеження
- Без `any` і `@ts-ignore` без коментаря-обґрунтування.
- Типи відповідей GraphQL тільки з codegen, руками не писати.
- Без зовнішніх сервісів (пошта, SMS, оплата) і без секретів у коді.
- Час тільки через інʼєктований Clock (у тестах він підміняється).
- Postgres = джерело правди; Redis/BullMQ лише тригери. Втрата Redis нічого не ламає.
- Інваріанти тримаються обмеженнями в БД, а не лише кодом.

## Процес
- Один коміт на етап роботи, CI зелений на кожному коміті.
- Перед комітом: typecheck, lint, codegen без змін, тести.
- README пиши англійською.
- Неоднозначності вирішуй сам і записуй у README, розділ «Прийняті рішення».

## Моделі субагентів
- Opus не використовувати. Для аналізу, конкурентності, обмежень БД, відновлення після втрати Redis і черги листа очікування, а також для ревʼю: Sonnet.
- Тільки для механічної роботи (сід, форми, i18n, yaml CI, README): Haiku.
- Модель кожного субагента вказуй явно при запуску.

## Економія токенів
- Тести запускай із `--reporter=dot` або тільки по одному файлу; повний прогін один раз перед комітом.
- Ніколи не виводь у чат повні логи й serialized errors: лише перші й останні 30 рядків або grep по ключових словах.
- Читай лише файли й розділи, названі в промпті; не роби широких пошуків.
- Ревʼюер: один раз на етап і лише по diff цього етапу.
- Роби коміт після кожного зеленого підетапу, не накопичуй.
